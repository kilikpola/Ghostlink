# Manual NAT Traversal Verification Protocol (Phase 2b)

Automated unit tests prove that the binding protocol, NAT type classification logic, simultaneous-open connection scheduling, and fallback mechanisms work correctly on localhost. However, real-world NAT behavior can only be verified with real NAT firewalls on separate networks.

This manual test is designed to be executed by a user running the interactive test harness script: [run-manual-nat-test.js](run-manual-nat-test.js).

---

## 1. Setting Up Public Peers (Bootstrap Nodes)

To discover external addresses and detect your NAT type, you must query **at least 2 distinct Public Peers**. You can set these up on a VPS or any public-facing machine that is NOT behind a symmetric NAT (e.g. has a public IP address).

### Running a Public Peer on a VPS:
1. Open a terminal on your VPS/public server and start a persistent shell session (e.g., via `tmux` or `screen`) so the process doesn't terminate when you disconnect your SSH session:
   ```bash
   tmux new -s gmp-bootstrap-1
   ```
2. Navigate to the `gmp-core/` directory and run the public peer:
   ```bash
   node test/run-public-peer.js
   ```
   *(Alternatively, run it in the background using `nohup` if you prefer: `nohup node test/run-public-peer.js > public-peer.log 2>&1 &`)*
3. Enter the port (e.g., `49500` for Peer 1) and press **Enter**.
4. Accept the default seed or enter a custom one.
5. The script will output a JSON configuration block. For example:
   ```json
   {
     "address": "<YOUR_VPS_PUBLIC_IP>",
     "port": 49500,
     "nodeId": "68df49dfdf62...",
     "addedAt": 1782657102834,
     "lastVerified": 1782657102834
   }
   ```
6. Detach from your tmux session using `Ctrl+B` then `D` (or exit SSH). The process will continue running persistently. To start the second public peer required for NAT classification, create a separate session (e.g. `tmux new -s gmp-bootstrap-2`) and run it on port `49503`.

### Configuring Client Nodes:
On both Device A (cellular) and Device B (home WiFi), open [public-peers.json](../data/public-peers.json) and replace the placeholder list with the JSON entries generated by your 2 public peer nodes:
```json
[
  {
    "address": "192.0.2.55", 
    "port": 49500,
    "nodeId": "68df49dfdf62..."
  },
  {
    "address": "192.0.2.55", 
    "port": 49503,
    "nodeId": "99ff5fce5aef..."
  }
]
```

## 2. Test Execution Steps

### Step 1: Run the helper script on both devices

Open a terminal on both devices, navigate to the `gmp-core/` directory, and run:
```bash
node test/run-manual-nat-test.js
```

Select the roles:
- **Device A (Cellular)**: Select `1` (Initiator). Press **Enter** for default seed and port `49501`.
- **Device B (WiFi)**: Select `2` (Responder). Press **Enter** for default seed and port `49502`.

---

### Step 2: Address Discovery & NAT Classification

Both clients will query the Public Peers configured in `public-peers.json`.

#### What to look for (Success Logs):
```text
[1/5] Initializing local GMP node...
      Local NodeID: 99ff5fce5aefed6cc0b842bab9f70b1fb041e4cfa5ec27e06e7dd079d231c68b601cabcd3aae2ec61f82358b4671c9d2faaa7f0eaedaec13ae1fabdd988363a6
      Listening on port 49501

[2/5] Performing address discovery & NAT classification...
      Loaded 2 public peers from public-peers.json.
      Querying peer 192.0.2.55:49500...
      -> Response: 198.51.100.4:56201  <-- indicates binding request sent & response received
      Querying peer 192.0.2.55:49503...
      -> Response: 198.51.100.4:56201
      Discovered Public IP/Port: 198.51.100.4:56201
      Discovered NAT Type: RESTRICTED_CONE <-- indicates NAT classification successful
```

#### What to look for (Failure Logs):
- **All public peers offline**:
  ```text
  Querying peer 192.0.2.55:49500...
  -> Failed: connect ECONNREFUSED 192.0.2.55:49500
  Failed to determine consensus public address: All public peer queries failed
  ```

---

### Step 3: Payload Exchange

The payload exchange is a **2-step process** between the Initiator and Responder:

1. **Device A (Initiator)** generates and prints a Base64 **invite payload** containing its NodeID, observed address, port, and NAT type. Copy this payload.
2. Send the invite payload to **Device B (Responder)** via any out-of-band channel (paste, QR code, messaging app).
3. **Device B (Responder)** decodes the invite, sets a coordinated timestamp 60 seconds in the future, and generates a Base64 **coordinated response payload** containing its own details plus `attemptTimestamp`. Copy this payload.
4. Send the coordinated response payload back to **Device A (Initiator)**.
5. **Device A (Initiator)** pastes the coordinated response when prompted: `PASTE RESPONDER (PEER B) COORDINATED RESPONSE PAYLOAD HERE:`

> **Important**: The Responder's payload is the one that contains `attemptTimestamp`. The Initiator's invite payload does NOT contain a timestamp — it is generated by the Responder after receiving the invite. Do NOT paste the Initiator's invite payload back into the Initiator prompt.

---

### Step 4: Coordinated TCP Hole Punching

Once payloads are exchanged, the connection countdown begins:
```text
[5/5] Executing Coordinated TCP Hole Punching...
[HolePunch] Waiting 43500ms until coordinated timestamp 1782657102834 to start hole punching...
```
At the target timestamp, simultaneous outbound connects begin:
```text
[HolePunch] Starting simultaneous-open TCP connections to <peer_discovered_ip>:<peer_discovered_port>...
```

#### What to look for (Success Logs):
```text
[HolePunch] TCP connection established! Running GMP handshake...
============================================================
🎉 SUCCESS: Direct connection established via hole punching!
Peer Authenticated NodeID: 68df49dfdf62d5a0f2eaba87069aa5634e1c3c711fafd4edd5e41e0b2fa0bd7f8f952aecb707cc3b571411a29746932a728d6a7894cbe1edf01d22c953b9c17f
============================================================
```

#### What to look for (Graceful Fallback Logs):
If hole punching fails due to symmetric NAT configuration on either side, it will print:
```text
============================================================
✗ FAILED: Hole punching failed.
Direct connection failed — this can happen with strict (symmetric) NAT on one or both sides. Falling back to QR/paste signaling or the optional relay.
============================================================
```

In either case, a timestamped test log will be saved:
```text
[Log Helper] Test log successfully written to: /path/to/gmp-core/data/manual-nat-test-<timestamp>.log
```
